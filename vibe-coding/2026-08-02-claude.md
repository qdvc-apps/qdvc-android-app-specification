### Your two items

**1. The phantom gap between the bottom navbar and page content — rewrite B2's "Insets" bullet as a proper subsection**

Both apps hit this. Root cause is the same in each: nested `Scaffold`s each applying the bottom system-bar inset on top of the outer Scaffold's bottom-bar reservation, so content stops ~1cm short of the bar. In nts there was a second additive cause — the content `Box` re-applying `WindowInsetsSides.Bottom` that the `NavigationBar` already owns.

I'd replace the one-line bullet with a stated contract: **exactly one owner per inset edge.** The outer `Scaffold` contributes nothing (`contentWindowInsets = WindowInsets(0,0,0,0)`); each screen's `TopAppBar` owns the top via its own default `windowInsets` (which is *why* zeroing the Scaffold's content insets doesn't break the top — worth stating explicitly, because it looks wrong); the bottom `NavigationBar` owns the bottom; and no inner `Scaffold` may contribute a bottom inset. Note the two equivalent forms the apps landed on — checklists uses `WindowInsets(0,0,0,0)` on all four tab Scaffolds, nts a shared `topOnlyInsets` = `systemBars.only(Top)` — and pick one as canonical (I'd take nts's named helper, since a named value is self-documenting and a full-screen route that legitimately wants default insets, like Settings, then stands out by *not* using it).

**2. A new haptics section (A9 user-facing + B14 technical)**

This is fully worked out in checklists (32 call sites behind one `Haptics` class) and entirely absent from nts — which is the strongest argument for spec'ing it. I'd lift it close to verbatim:

- **Mechanism:** `View.performHapticFeedback`, never `Vibrator`/`VibrationEffect`. Three reasons, all worth recording: it honours the system's own touch-feedback setting, it needs no `VIBRATE` permission (both apps declare zero permissions), and it no-ops on a device with no vibrator. Deliberately without `FLAG_IGNORE_GLOBAL_SETTING`.
- **Six named sensations** — `tap`, `step`, `pickUp`, `drop`, `confirm`, `reject` — each mapped to a constant, with the API-30 ones (`GESTURE_START`, `GESTURE_END`, `CONFIRM`, `REJECT`) behind version guards and named `minSdk 26`-safe fallbacks.
- **The three intensity rungs**, as a table: `CONTEXT_CLICK`/`CLOCK_TICK` faint, `VIRTUAL_KEY`/`KEYBOARD_TAP` normal, `LONG_PRESS` heavy. This is the dial, documented so nobody re-derives it.
- **A trap:** `CONTEXT_CLICK` is the platform's *lightest* predefined effect (≈`EFFECT_TICK`). It reads as broken haptics on a device where every other app feels right. Taps get `VIRTUAL_KEY`.
- **A rate-limiting rule:** a repeating sensation (`step`) takes the faintest rung, and must be gated on crossing a boundary — a row passing a neighbour, a swipe crossing its commit threshold — so it can't buzz continuously.
- **Two silence rules:** a disabled control never buzzes (it would imply something happened), and a gesture that grabbed nothing never buzzes (a long press on empty space below the last row).
- **An event→sensation mapping table** as the recommended default, so a new app doesn't relitigate it.

### High-value changes I'd also propose

**3. B0's `adjustResize` is wrong, and the keyboard is a separate trap from the navbar gap**

nts spent four rounds on this. `enableEdgeToEdge()` sets `decorFitsSystemWindows = false`; combined with the manifest's `adjustResize` the keyboard gets counted twice. Worse, and this is the non-obvious part: a composer that sits above the app's own `NavigationBar` and applies `imePadding()` over-lifts by the *entire bar* — bar content **plus** its inset — and the intuitive fix, `ime.exclude(navigationBars)`, only subtracts the inset, leaving most of the gap (~2.5cm on the reporter's device). The resolution: `windowSoftInputMode="adjustNothing"`, hide the bottom `NavigationBar` while `WindowInsets.isImeVisible`, and apply a single plain `imePadding()` to the bottom-most element.

I'd spec this **conditionally**, because checklists still ships `adjustResize` and has never hit it — it has no bottom-anchored input. So: `adjustResize` is fine while no surface anchors an input to the bottom; the moment one does, switch to `adjustNothing` + hide-on-IME. B0's current unconditional `adjustResize` line has to go either way.

**4. Add the "projection-first" data architecture as a recognised alternative to B10**

Architecturally the largest item, and I think the most valuable. B10 today treats Room as a *search* cache with a live-scan fallback. checklists went considerably further: Room is the read model for **everything** — opening a checklist, switching, ticking, reading an item's history are all SQL, and nothing in normal use touches SAF to read. Writes go the other way and go *immediately*, never queued or batched, explicitly because the files are shared with a desktop peer and a deferred write is a write that can be lost.

That's a genuinely better answer to B3's "SAF calls are expensive" than the current one, so it deserves to be in the spec — but as an alternative with a decision rule, not a replacement. Roughly: **projection-first** when state is derived from many small files (append-only logs) or a desktop peer edits the same tree; **cache-with-fallback** (B10 as written) when items are self-contained and a read is one file. With it come the rules that keep it safe: the projection holds nothing not already on disk so it stays disposable (`fallbackToDestructiveMigration`, schema bumps just rebuild); marks patch the projection optimistically then write, rolling back *and telling the user* on failure; structural writes go to disk first, because that's where naming and uniqueness are validated, and the projection refreshes from the result.

**5. And with it, a user-facing loading screen (new A-section)**

If launch does a full read, the app blocks — so make the block legible. checklists narrates the scan as a terminal-style transcript rather than showing an opaque spinner, and the log is explicit that the transcript is also where an unreadable folder or a missing `checklists/` becomes visible. Small section, clear rationale.

**6. Drag-to-reorder should replace up/down arrows as the canonical gesture (A4, B6)**

The spec calls drag "explicitly out of scope for now"; checklists shipped it and it carries real hard-won detail worth recording:

- Start on **long press**, not plain drag — a plain drag consumes the list's scroll gesture, leaving a list taller than the screen unscrollable while in the mode.
- The reordering list must contain **only draggable rows**. The index arithmetic assumes list index equals row index, so a pinned header or spacer inside the same lazy list breaks it *silently*. checklists pins its info zone above a list of nothing but rows.
- Autoscroll near the edges.
- The **draft order is never persisted**, which is what makes a force-quit discard it for free.
- The mode is **hoisted to the ViewModel**, because the tab bar and the back handler both need to see it; the tab bar slides out of the way; Cancel and Save each confirm; system back triggers the discard confirmation.
- Feed `onMove`/`onDragStart`/`onDragEnd` into the haptics from item 2.

I'd keep up/down arrows as the documented low-cost fallback rather than deleting them.

**7. Scroll-position retention across tab switches (A8 + a B subsection)**

Neither app got this right first time; checklists needed two attempts and a shared helper. The trap is structural and non-obvious: the `AnimatedContent` that swaps tabs **discards the outgoing tab's composition**, so an implicitly-remembered `LazyListState` is rebuilt at zero on every return — and `rememberSaveable` does *not* help, because it survives configuration change rather than leaving composition. The fix is to hoist list state above the `AnimatedContent`, key it per item/workspace, and prune keys to what's still open so it can't grow over a long session. Plus the judgement call, which is worth stating so it isn't treated as an oversight: search results, reorder lists, and Settings should deliberately reset to the top.

**8. Tab-switch motion is a second, distinct vocabulary (A2 "Motion" / A8 / B7)**

A8 currently says one vocabulary — the horizontal slide — is reused for all hierarchical navigation. checklists added a separate "card-shuffle" for *lateral* tab switches (incoming scales up and fades in, outgoing recedes aside). That's correct rather than a violation: tabs have no depth relation to one another, so a directional slide would imply an ordering that doesn't exist. I'd spec both axes explicitly, and note that the lateral transition needs the **same** `SizeTransform { _, _ -> snap() }` guard — it's the identical failure mode as B7's diagonal drift.

**9. A new Part B section on Room/KSP traps**

Three concrete ones from checklists, all generalisable, all cost real time:

- **Never name a DAO parameter `new`** (or any Java reserved word). Room's KSP processor generates *Java*, so it emits `_stmt.bindString(_argIndex, new)` and the build fails in generated code. Audit every DAO parameter, entity property and projection field against the Java keyword list.
- **Never call a synchronous Room query from the main thread.** Without `allowMainThreadQueries` it throws — checklists crashed on every workspace open this way.
- **An id field must name what it identifies.** A `WriteResult.docId` meaning "the folder this write touched" was the checklist for some operations and the node for others; the caller read it as the checklist's unconditionally, deleted the real row, and re-inserted the *node* as a checklist. The generalisable lesson is that one field silently meaning two things passes review precisely because the two meanings coincide in the common cases.

**10. B3 needs an append-mode writing subsection**

Currently B3 mentions only `openOutputStream(uri, "wt")`. Appending is unmentioned and is a data-loss trap when a plaintext file is shared with other clients: `"wa"` writes onto the final byte, so if the last line lacks a terminator you fuse two valid rows into one malformed row and **destroy both**. Rules: classify the final byte (accept CR *and* LF, so CRLF and bare-CR files work) and supply the missing separator first; find the tail by streaming to the end rather than trusting a directory listing's `size`, which is stale precisely when another client has just written; on an indeterminate tail fall back to rewrite rather than appending blind. Plus the adjacent latent bug this exposed, which generalises well beyond logs: a read helper returning an empty list for *both* an empty file and a failed read makes the rewrite fallback truncate the file.
